# バーニングニーズ調査マニュアル

> 別のエージェントへ渡すための単独で読めるMarkdown版。PDF・Word・Excelを開かなくても、調査手順、判定基準、出典、記入用テンプレートを利用できる。
> 公開情報の確認日：2026年10月17日。特定業界の選定・新しい案件の実査は、この文書を受け取った後の作業となる。

公開情報から課題を見つけ 何を誰に提供するか決める

対象：小規模なチームがAIを使って作る業務サービス・SaaS。国内B2Bを主例にする。B2Cでは利用者と購入者、価格、購入頻度を読み替える。公開情報の確認日：2026年10月17日。

### 最初にすること

最初の調査先は、すでに人やお金を使っている仕事の募集・依頼と、既存製品の利用者レビュー。そこで見つけた困りごとを現行製品の機能と照合し、解消されていない狭い場面を探す。その場面の当事者に確かめ、範囲と価格を決めた小さな有料提供で検証する。

### このマニュアルでの定義

**バーニングニーズとは、特定の人・組織が、特定の状況で必要な結果を得られず、放置すると無視できない損失が生じ、その回避のために今または次の発生時に時間・お金・手間を投じて解決しようとしている状態。**

「便利そう」「不満が多い」「検索数が多い」だけでは認定しない。年1回でも期限と損失が大きければ強い需要になり得る。毎日の軽い不便でも、対策する理由がなければ弱い。

| 順番 | すること | 残す成果 |
| --- | --- | --- |
| 1 | 業種・担当者・発生場面を1つ選ぶ | 対象を説明する1文 |
| 2 | 依頼・レビュー・質問の原典を読む | URL付きの証拠記録 |
| 3 | 同じ状況の課題を束ねる | 課題仮説と未確認事項 |
| 4 | 現在の代替手段と反証を確認 | 何が今も残るか |
| 5 | 需要・獲得・提供条件を別々に評価 | 追加調査の優先順位 |
| 6 | 本人に確認し、価格付きで小さく提供 | 支払・成果・継続の実績 |

ネット調査で分かるのは有望な仮説まで。新サービスへの支払意思、実データでの成果、継続、集客の採算は別に確認する。点数や件数の目安は本書の運用案であり、売れる確率を保証する基準ではない。

使い始める順番：探す場所 → 検索 → 記録 → 判定 → 提供案 → 聞き取りと有料試行。研究の背景と、本書への取り入れ方も次の2章で説明する。

## 1 米国の実務体系と学術研究を使い分ける

「研究された方法」と「広く使われる方法」は分けて扱う。下記の理論・研究を組み合わせて本書の調査手順を設計した。独自の10点表や3件という目安が研究で実証されたわけではない。

| 手法と原典 | 裏付けの種類と限界 | 本書で取り入れること |
| --- | --- | --- |
| Customer Discovery<br>米国 NSF I-Corps | 公的な起業教育の実務体系。採用実績は、全業種での成功を保証する因果的証明ではない。[S10] | 外へ出て当事者と決裁者に会い、顧客・価値・購入経路を確認する |
| Jobs to Be Done<br>Christensenら | 顧客が状況の中で実現したい進歩を捉える概念・事例に基づく方法。[S11] | 属性や希望機能だけでなく、直近の場面、目的、採用した代替手段を聞く |
| Lead Users<br>MIT von Hippel 1986 | 強い先行需要を持つ利用者を探す研究。先行層の特殊性を一般市場へそのまま広げない。[S12] | 自作・改造・回避策に既に労力を使う人を探す |
| Need Solution Pairs<br>von Hippel・Kaulartz 2021 | ネットの課題と利用者の解決策を組で探す事例研究。対象はカイトサーフィン。購買や売上の実証ではない。[S13] | 困りごとの投稿と、自作ツール・工夫を関連付けて読む |
| 科学的な起業判断<br>Camuffoら 2020・2024 | 2024年論文は伊・英の759社、4つの無作為比較試験。案の終了と、絞った方向転換などに効果。日本のAI事業への成功保証ではない。[S14] | 反証できる仮説、計測項目、事前の中止条件を決める |
| 支払意思の測定<br>Schmidt・Bijmolt 2020 | 消費財に関する77研究のメタ分析。仮想の支払意思と実際の金銭条件に差。B2Bの補正率は示さない。[S15] | 「払うと言った」と、実際の有料試行を分ける |

### 本書としての結論

ネットで候補を探し、当事者の行動と状況を理解し、既存手段で残る不足を確かめ、価格付きで試す。最初から「この業種のSaaSを作る」と決めず、証拠が変われば対象・提供・中止の判断を変える。

I-CorpsのNational Teamsには7週間で100件以上の面談という参加要件がある。これはその教育プログラムの要件であり、本書の全案件に100件を課す根拠にはしない。[S10]

## 2 研究を検索と判断に落とし込む

### 不満に加えて 自作した解決策を探す

課題と解決策を組で探す研究を、本書では次のように応用する。GASやLLMなど現在の道具に展開する部分は本書の実務案であり、引用論文が特定LLMの精度を検証したものではない。[S13]

| 探すもの | 検索語の追加例 | 次に確かめること |
| --- | --- | --- |
| 自作と改造 | ［業務］ 自作／GAS／スクリプト／Excel<br>［業務］ built my own／workaround | 何を解決したか。作るほど困った理由は何か |
| 既存手段の穴 | ［製品］ 手作業／連携できない<br>［製品］ manual／missing feature | どの条件で失敗し、何が今も残るか |
| 代替を探す動き | ［製品］ 代替／乗り換え<br>［製品］ alternative／switching from | 何がきっかけか。移行の不安や負担は何か |
| 運用の限界 | ［業務］ 毎月／残業／保守<br>［業務］ maintenance／too time consuming | 自作で十分か。他の人にも同じ負担があるか |

海外の投稿は、使用製品・役割・国・商慣行も記録する。同じ制度や支払習慣とは限らないため、米国の課題をそのまま国内需要と数えない。日本の当事者で発生条件を確かめる。

### 何を買うかより どの状況を変えたいかを読む

Jobs to Be Doneの観点では、たとえば「CSVが欲しい」を、締め前に何を終え、誰へ渡し、どんな失敗を避けたいかまで戻して聞く。機能を提案する前に、現在の手段を選んだ理由と、変更をためらう理由も残す。[S11]

### 主張を外れる可能性のある予測にする

| 仮説の悪い書き方 | 実験できる書き方の例 |
| --- | --- |
| 経理担当は面倒な作業を減らしたい | 対象条件に合う担当者が、直近の照合で残る負担を実例と作業量で説明できる |
| AIで自動化すれば売れる | 現行製品では残る同一条件を持つ対象5社へ、同じ範囲と2万円の試行を提示し、2社が支払う |
| 便利なサービスになった | 許可されたデータで事前に決めた見落とし数・確認時間・納期を満たし、次回も購入される |

数字は説明用の仮説。対象の選び方、期間、価格、合格条件を先に書き、不合格ならどの前提が外れたか確認する。返信がないだけでは課題不在とは断定できないので、対象に届いたかと、提案の理解を分けて調べる。[S14]

AIには抽出・分類・反証候補の作成を任せる。採点に使う根拠と上位候補は人が原典を開いて確認する。AIが作った人物、発言、金額、URLを実データとして使わない。

## 3 調べる対象と場所を決める

### 対象を業種だけで決めない

「中小企業の効率化」では広すぎる。「誰が、どの業務を、どのタイミングで終えられないか」まで狭める。自分が当事者に話を聞ける、既存ツールを触れる、継続して観察できる領域から始める。

対象の型：［業種・規模］の［役割］が、［締め日・納品・人員不足などの場面］で［完了したい仕事］を進められない。

探索用の例：EC企業の経理担当が月次締めで証憑を揃える場面／工事会社の事務担当が請求前に写真・作業記録を揃える場面。いずれも探索の入口であり、需要を確認した結論ではない。

### この順番で公開情報を読む

| 優先 | 場所と入口 | 取りたい証拠 | 読んだだけでは分からないこと |
| --- | --- | --- | --- |
| 1 | CrowdWorks・Lancers・求人サイト<br>業務名＋募集／代行／依頼 | 発注成果、作業内容、予算、期限、現在のツール | 募集額は支払実績ではない。人を任せたいだけかもしれない |
| 2 | ITreview・ITトレンド・アプリレビュー<br>製品名＋改善点 | 利用条件、良い点、残る不満、回避策 | 古い版・別プランの不満、投稿促進、匿名の重複 |
| 3 | 公式コミュニティ・GitHub Issues・質問サイト | 再現条件、未解決期間、手動回避、試した対策 | 一時的な障害か、現在も続いているか |
| 4 | X・note・Reddit・業界ブログ | 現場の言葉、発生場面、失敗や作業の記録 | 共感・いいねは購入者数ではない。体験談か伝聞か |
| 5 | 競合の公式機能・料金・ヘルプ・更新履歴 | 何がどの条件と費用で提供されているか | 広告上の機能が対象者のデータで動くか |
| 6 | Google検索・Trends・Keyword Planner | 調べる言葉、季節性、購入前に通る検索 | 検索した理由、購入者数、実際の獲得費 |

### 始めるときの条件

原典の本文を開ける情報から始める。登録が必要な場所は、見える範囲と未確認部分を記録する。Keyword Plannerはアカウント設定・支払情報等が必要な場合があるため、初回調査の必須条件にしない。[S4]

Trendsの0〜100は相対値で、少量の検索は0になることもある。検索数が少ないB2Bでも、紹介や業界ネットワークで成立する可能性は残る。[S3]

## 4 検索を実行する

### 4つの方向から同じ業務を見る

［業務］に調べたい作業名、［製品］に現在よく使われるツール名を入れる。広い「AI 活用」から始めず、当事者が使う名詞と動詞を使う。下記は検索語のひな型で、全件を機械的に消化する必要はない。

| 目的 | コピーして置き換える検索語 |
| --- | --- |
| 支出と行動 | ［業務］ 代行 依頼<br>［業務］ 募集 継続<br>site:crowdworks.jp/public/jobs/ ［業務］<br>site:lancers.jp/work/detail/ ［業務］ |
| 切迫した場面 | ［業務］ 間に合わない<br>［業務］ 月末 手作業<br>［業務］ やり直し<br>［業務］ ミス 確認 |
| 現行の不満 | ［製品］ できない<br>［製品］ 二重入力<br>［製品］ 乗り換え 理由<br>site:itreview.jp ［製品］ 改善 |
| 反証と購入意図 | ［製品］ ［不満の機能］ ヘルプ<br>［製品］ ［不満の機能］ リリース<br>［業務］ 比較 料金<br>［業務］ Excel テンプレート |

### 実行手順

- 最初は直近12か月を優先する。結果が少なければ期間を広げ、公開日を残す。法改正・季節・製品更新が関係する場合は、その前後を分ける。

- 検索結果を10件程度読み、条件に合う原典を開く。本文を読めないスニペットは「発見のみ」にして採点根拠にしない。

- 原典から、発生場面・損失・現在の対策・未解決点を抜き出す。実際に使われた言葉を次の検索へ足す。

- 同じ課題を別の当事者・別の種類の媒体で探す。反対に、満足している利用者や解決済み情報も探す。

- 候補ごとに、検索語・期間・媒体・原典URL・読めたか・採用／除外理由を残す。都合のよい投稿だけを採らない。

### 90分で見つからなかったら

現場の呼び方に1度変える。「消込」なら「入金確認」「明細照合」。それでも乏しければ公開情報不足として面談か保留へ進む。検索結果件数は市場規模、広告の多さは獲得採算の証明に使わない。

## 5 証拠を記録し 課題を束ねる

### 記録は1当事者の1つの状況で1行

このファイル末尾の「証拠記録テンプレート」に入力する。長い投稿に異なる課題があれば分け、同じ証拠IDを関連付ける。原文、要約、推測を混ぜない。公開情報にない金額・損失・役職はUまたは未確認とする。

| 必須の記録 | 書く内容 |
| --- | --- |
| 識別と原典 | 証拠ID、課題ID、URL、媒体・出典種、公開日、確認日 |
| 当事者 | 役割、業種・規模、確認根拠、同一人物／企業の重複グループ。匿名は匿名と書く |
| 事実 | 困った場面、完了したい仕事、損失、期限・頻度、現在の対策、支出や作業時間 |
| 条件 | 製品・プラン・版、対象データ、件数、制約、試した方法、まだできないこと |
| 根拠の性質 | 本人の経験、発注、伝聞、販売者の説明、分析者の推測を分類 |
| 判定と反証 | どの採点項目を支えるか、現在も未解決か、反対の事実、次に確かめること |

### まとめる単位は機能名より発生場面

「CSV出力がほしい」をそのまま課題にしない。「月末に複数拠点の明細を統合し、経理へ渡すのに転記が必要」のように目的を特定する。同じ目的・同じ制約・同じ支払主体ならまとめ、異なる場合は分ける。

課題の記述式：［誰が］［きっかけ］に［結果］を得たいが、［障害］でできない。［期限・頻度］まで放置すると［損失］が出る。現在［代替手段］に［費用・時間］を使うが、［不足］が残る。

### 独立した証拠だけを数える

- 同じ人のXとnote、転載記事、同じ企業の同一障害は原則1件。投稿数・いいね数を顧客数にしない。

- 匿名で同一企業か判別できない場合は、独立性を確認できた数に足さない。別業種などの手掛かりは別欄に残す。

- 販売者の導入事例は提供機能・活用条件の参考。別の当事者による不満の証拠としては数えない。

- 古い不満を使うときは、現在の公式機能・ヘルプ・変更履歴を確認。判別できなければ未解決と断定しない。

公開情報は代表標本ではない。困っていても投稿しない人、投稿をやめて解約した人、満足している人を取りこぼす。件数は仮説の反復確認に使い、市場の何％が困るかへ外挿しない。

## 6 需要の強さを判定する

需要は5項目で見る。0＝弱いと確認、1＝一部確認、2＝具体的に確認、U＝未確認。Uを0点として埋めない。点数には必ず証拠IDを添える。同じ仮説でも利用者と決裁者の答えが違えば両方記録する。

| 項目 | 0 弱いと確認 | 1 一部確認 | 2 具体的に確認 |
| --- | --- | --- | --- |
| D1 急ぐ理由 | 延期しても支障がないと本人が説明 | 期限・頻度はあるが、延期の影響は不明 | 期限や次の発生場面が分かり、先送りできない理由がある |
| D2 放置の損失 | 好み・見栄え程度で実害がない | 手間・ストレス・ミスがある | 残業・失注・未回収・作業停止等の実例と規模がある |
| D3 解決行動 | 対策の必要がないと本人が説明 | 検索・比較・相談・試用をした | 外注・購入・予算申請・乗換作業・反復する手作業がある |
| D4 既存手段の不足 | 許容できる負担で必要な結果を達成 | 許容できる軽微な不便が残る | 必要な品質・時間・費用の条件で結果を得られない、または回避策の負担が許容範囲を超える |
| D5 支払主体と経路 | 支払う予定がないと確認 | 利用者・決裁者は分かるが、予算か時期が不明 | 支出・予算、支払う主体、購入時期を確認できる |

### 合計の使い方

全項目が埋まった場合だけ10点満点を計算する。1つでもUなら「判定未完了」とし、分かっている項目を見ながら不足を調べる。新サービスへの支払実績は、この点数とは別に管理する。

追加調査を優先する初期目安：8点以上、D2・D3・D4が各2、独立当事者3以上、原典の種類2以上。これは担当者の調査順を揃える運用案で、需要認定・開発承認ではない。業界ごとに調整できる。

低い合計やUだけで捨てない。原典が足りない場合は追加調査。現行手段で解決済み、支払う予定がないなどの反証があれば、合計で相殺せず仮説を見直す。

### 判定が割れたとき

2人が同じ原典を読み、差が出た項目だけ話し合う。「なぜ2点と思うか」ではなく「どの文章・行動で2点と確認できるか」を示す。根拠がなければUへ戻す。残る不一致は次の聞き取り質問にする。

例：毎月Excelで照合している事実はD3の材料になる。しかし、それだけでは損失規模・既存製品の不足・ソフトへの支払意思は分からない。各項目を一緒に引き上げない。

## 7 届けられるか 提供できるかを分ける

### 獲得可能性は別の8点満点

| 項目 | 0 | 1 | 2 |
| --- | --- | --- | --- |
| A1 対象者の識別 | 広すぎて見分けられない | 業種・役割等は分かる | 使う製品や発生条件まで見分けられる |
| A2 接点 | 現時点で接点がない | 検索語・媒体の候補がある | 対象者が実際にいる具体的な経路を確認 |
| A3 購入タイミング | 必要時期に接触できない | 発生周期・契機は分かる | 切迫する時点に接触できる経路を確認 |
| A4 獲得の実績 | 適切な条件で試したが目標未達 | 適格な相談・試用等はある | 設定した費用・期間内で有料顧客を獲得 |

未測定はU。ネット調査だけならA4は通常Uになる。需要点と足さない。A4の目標は実験前に決め、失敗した経路と条件も残す。検索で人が見つかることと、自社が獲得できることを分ける。

### 提供条件は はい いいえ U で確認

| 条件 | はい とする証拠 |
| --- | --- |
| P1 結果を出せる | 対象データ・実作業で必要な精度、所要時間、成果を達成 |
| P2 導入できる | 権限、データ入手、連携、移行、社内承認の条件を満たす |
| P3 採算が合う | 提示価格に対してAI・人手確認・導入・保守等の原価と獲得費を確認 |
| P4 責任を担える | 誤りの検知と修正、例外対応、担当者の役割を実行できる |

### 段階は証拠を見て手動で進める

| 段階 | 次に進める条件 |
| --- | --- |
| 探索メモ | 原典が見つかった。まず状況と未確認事項を埋める |
| ネット上の有望仮説 | 同型の具体的課題が独立した複数当事者で反復し、現行でも残る根拠がある |
| 当事者確認済み | 直近の実例、対策、支出・決裁、切替条件を本人に確認 |
| 有料検証済み | 範囲・価格・納期を明示し、対象顧客が実際に支払った |
| 継続提供の見込みあり | 成果、再利用・再購入、獲得費・提供費を観測した |

無料登録、好意的な感想、見積依頼、発注予定、入金、成果受入、継続購入は別の記録にする。支払い1件で市場全体や拡大可能性まで確認したことにはならない。[S1]・[S2]

## 8 既存提供を比較し 小さな提供案に変える

### 比較は顧客が今している方法から

競合SaaSだけでなく、Excel、汎用AI、社員の手作業、外注、何もしない方法も同じ条件で比較する。「機能の数」ではなく、対象者が必要な結果に到達するまでの時間と総費用を見る。

| 比較する内容 | 確認すること |
| --- | --- |
| 対象と結果 | 同じ業種・規模・件数・データ形式・処理期限で使えるか |
| 現在の方法 | なぜ選んだか、良い点、残る手作業・例外・ミス |
| 実際の総費用 | 基本料、従量、オプション、初期費、移行、教育、確認作業、税の条件 |
| 導入の壁 | 既存データ、権限、取引先・上司の承認、信用、業務変更の必要性 |
| 今も残る不足 | 公式仕様・ヘルプで解決しないか。利用者の実データで再現するか |

### 不満の種類で提供を変える

| 見つけた原因 | 最初に試す提供 |
| --- | --- |
| 既存機能を知らない・設定できない | 設定代行、導入支援、操作説明。新規開発の前に解消できる |
| 入力元・出力先の形式が合わない | 1業務・1形式に絞った変換や連携。例外を人が確認できるようにする |
| 成果に至るまで担当者の手作業が残る | 成果物を納品するサービスから始め、反復部分を段階的にソフト化 |
| 機能は足りるが高い | 同じ対象範囲で総費用と切替負担を比較。安さだけなら原価優位を先に確認 |
| 同じ例外が複数社で繰り返す | 例外の処理・確認・再実行に絞った機能を、実データで検証 |

### 提供案を1文と条件にする

［対象者］に、［発生場面］までに、［成果物／到達結果］を提供する。現在の［方法］に残る［不足］を減らす。対象範囲は［件数・形式］、価格は［金額と課金単位］、提供期間は［日数］、合格は［測定条件］とする。

架空例：毎月の明細照合に困る卸売会社へ、指定2形式・月500行までの不一致一覧を翌営業日に納品する。料金は試行1回2万円。未一致の見落とし件数と担当者の確認時間を測る。金額・件数は説明用で、相場や支払意思を示さない。

利用者が欲しい結果、決裁者が払う理由、切替の壁を越える仕組みが揃うまで、機能一覧を増やさない。汎用AIや既存機能で十分なら、運用支援へ変えるか、その仮説を終了する。

## 9 公開情報で実際に判定する

### 実例 経理の外注募集から始める

2026年10月13日のCrowdWorks掲載例では、既存のマネーフォワード利用下で、証憑の取得・照合、不明取引の整理を含む経理業務を募集している。本文は月30時間・時給1,200〜2,000円、概要は週30時間・時給1,000〜1,500円で不一致。確認時は募集終了・契約1人表示だった。[S5]

| 需要項目 | 判定 | 理由 |
| --- | --- | --- |
| D1 急ぐ理由 | 1 | 月次の場面はあるが、先送りの影響は不明 |
| D2 放置の損失 | U | 作業量は示されるが、損失規模は不明 |

**結論：合計は判定未完了。独立当事者1社の探索メモとして残す。次は作業内訳と未解決条件を聞く。新しい経理SaaSを開発する根拠には足りない。**

## 10 当事者に確認し 有料提供を試す

### 最初の20分は最近の実例を聞く

相手は利用者だけでなく、必要に応じて決裁者も含める。冒頭で調査目的と所要時間を伝え、許可を得て記録する。質問の前半で自分の製品案を説明すると、相手がそれに合わせて答えやすくなる。

| 質問 | 確認する根拠 |
| --- | --- |
| 直近で困ったのはいつですか。最初から順に教えてください | 実際の作業・画面・成果物。記憶による説明ならその旨 |
| どこで止まり、何件・何時間・いくら影響しましたか | 損失の範囲、発生頻度、計測か推定か |
| 何もしないと、いつ何が起きますか | 次の期限と先送りできない理由 |
| 直近で何を試し、何にお金や時間を使いましたか | 購入・外注・手作業の実績。対策しなかった理由も聞く |
| 今の方法の良い点と、残る問題は何ですか | 守るべき価値、未解決の条件 |
| 誰が使い、誰が払い、どの承認が必要ですか | 支払主体、予算、判断時期、セキュリティ・連携条件 |
| 過去に似た道具をどこで知り、どう決めましたか | 実際の獲得経路、比較対象、切替理由 |

### 最後に範囲と価格を付けて提示する

提示するのは対象業務1つ、期間1回、測れる結果1つ。対象データ、件数、納品物、価格、納期、人が確認する範囲、失敗時の扱いを揃える。「あったら使いますか」への賛成は購入の証拠にしない。

- 段階を残す：関心表明 → データ・日程の提供 → 条件合意 → 入金 → 成果受入 → 再購入。途中の状態を入金と混同しない。

- 最初は人手を含む小さなサービスでもよい。担当者を隠して完全自動と説明せず、成果と原価を実測する。

- 許可されたデータで、処理前後の作業時間、例外数、誤り、手戻り、納期を測る。速くても確認の負担が増えれば改善ではない。

- 知人、特別な割引、特別対応での購入は記録する。通常条件で再現するかを別に試す。

実験前に「何が確認できれば次へ進むか」を書く。例：対象5社への価格提示で2社が有料試行、2社とも合格条件を満たす。これは設計例であり標準的な成約率ではない。対象外の相手や無料提供を分母・分子へ混ぜない。[S2]

## 11 集客と採算まで検証する

### 見つけた場所と 売れる経路を分ける

| 経路 | 確かめること | 最初の小さな実験 |
| --- | --- | --- |
| 課題名での検索 | 比較・料金・代行など購入に近い意図か | 具体的な作業と成果を説明するページから相談を受ける |
| 業界・職種コミュニティ | 同じ課題を抱えた人がいるか。案内が許可されるか | 質問への有用な説明と、希望者向けの診断案内 |
| 紹介・協業 | 会計事務所、業務代行、業界支援者等がその場面に関わるか | 対象と紹介条件を揃え、少数の案件で確認 |
| 求人・発注サイト | 今予算を付けている業務と提案の成果が合うか | 利用規約と募集の趣旨に沿った個別提案 |
| 既存顧客・本人の接点 | 近い業務と新しい顧客にも再現するか | 実績を基に同条件の別企業へ提案 |

公開された連絡先や投稿は、無差別な営業送信の許可ではない。まずその場所のルールと相手の意向を確認する。今回の作業は調査とマニュアル作成で、応募・送信・広告出稿は実施していない。

### 実験記録で数える項目

対象条件／経路／期間／接触数／返信数／適格商談数／価格提示数／有料顧客数／入金額／広告・外注費／営業時間／納品原価／成果受入／再購入。分母と計測期間を固定し、経路別に残す。

| 計算 | 意味と注意 |
| --- | --- |
| 獲得費 ÷ 新規有料顧客数 | CAC。獲得費には広告・紹介料・営業外注と営業工数の原価を含める。0社なら未成立で、0円にしない |
| 税抜売上 − 提供変動費 | 提供後に残る額。AI/API、手動確認、支援、決済手数料等を含める。初期導入費と継続月の費用を分ける |
| CAC ÷ 月次の提供後利益 | 安定継続を仮定した回収月数の目安。利益が0以下なら回収不能。継続実績がない段階では仮定値 |

架空の計算：獲得費6万円・有料3社ならCAC2万円。月額1万円・月次変動費4千円なら月次で残る額は6千円、単純回収は約3.3か月。導入原価・解約・固定費は別に見る。この値を市場実績として使わない。

「10時間短縮×時給」は空いた能力の評価で、現金支出の削減とは限らない。削減できる外注費・残業・失注を分ける。未観測の継続期間から高いLTVを作って、赤字の集客を正当化しない。

## 12 誰でも回せる運用手順

### 最初の1テーマを半日で調べる

| 時間目安 | 作業 | 終了条件 |
| --- | --- | --- |
| 0〜20分 | 業種・役割・発生場面を決める | 1文で対象を説明できる |
| 20〜90分 | 依頼とレビュー等の原典を読む | 証拠記録と検索履歴を残す |
| 90〜130分 | 同型課題の反復と反証を調べる | 独立性、現行機能、矛盾を記録 |
| 130〜180分 | 需要・獲得・提供条件を評価 | Uと次の確認方法が分かる |
| 180〜240分 | 提供案と集客実験を1つ作る | 進める／追加調査／保留／棄却を理由付きで決定 |

時間は初期目安。原典が揃えば早く終える。揃わなければ大量収集を続けず、用語の変更か当事者確認へ切り替える。初週は1〜3仮説に絞り、聞き取りの予定は相手の都合に合わせる。

### 調査担当から渡す1枚

対象者と場面／課題1文／独立した根拠とURL／現在の代替手段と総費用／現行でも残る不足／需要5項目とU／具体的な集客経路／最小提供と価格仮説／最大の反証／次の実験と停止条件。台帳のIDで原典へ戻れるようにする。

### AIへ渡す調査指示のひな型

「対象は［業種・役割・場面］。公開原典を開き、事実と推測を分けて記録してください。URL、公開日、確認日、当事者、損失、期限、対策、支出、製品条件、未解決点を抽出。見つからない項目はU。転載と同一当事者を重複計上しない。現行公式機能・料金・ヘルプで反証も調べる。提供仮説は最後に、根拠IDと未確認事項付きで3つ以内。ログイン回避、応募、送信、出稿、課金はしない。」

### AIへ渡す反証指示のひな型

「この仮説が売れない理由を調べてください。既存機能で解消済み、使い方の問題、支払主体不在、一時的な障害、特殊な1社、汎用AIで十分、切替費用が上回る可能性を確認。原典にない理由は推測と表示し、何を聞けば否定・確認できるか示してください。」

### 止める条件と見直す条件

現行製品で解決できるなら導入支援か別の不足へ。支払者が不明なら決裁確認へ。実験が不合格なら対象・成果・価格・経路のどこで離脱したかを1つずつ見直す。同じ条件で何度も調査・開発しない。反証が明確なら棄却し、記録を残す。

```text
3. 証拠をID付きで記録する。同一人物・企業・出来事の重複は除く。
4. 現在の公式機能・料金・ヘルプと、手作業・外注・汎用AIを比較する。
5. 需要D1〜D5、獲得A1〜A4、提供P1〜P4を別々に判定する。
6. 未解決条件に絞った提供仮説と、最初の獲得経路を作る。
7. 最も重要な未確認事項を検証する、価格付きの小さな実験案を作る。

判定ルール：
- 0・1・2は根拠があるときだけ使い、未確認はUとする。
- Uを0として合計しない。需要点と獲得点を足さない。
- 追加調査の優先基準は作業用の目安で、成功確率や開発GOではない。
- ネット上の発言や募集額から、新サービスへの支払意思を断定しない。
- 実例、架空例、事実、推測、計画、実施結果を分ける。
- 原典を読めない場合は「発見のみ」とし、読んだことにしない。
- 反証と、既存手段で解消できる可能性を必ず調べる。

成果物：
1. 推奨する次の調査または実験を、理由付きで最初に説明する。
2. 各候補について、本書末尾の5つの記録テンプレートを埋める。
3. 原典URL、公開日、確認日、独立当事者数とその数え方を残す。
4. 進める／追加調査／保留／棄却を、根拠と未確認事項付きで示す。

この依頼の範囲は公開情報の調査と文書作成まで。
応募、営業送信、広告出稿、課金、ログイン回避、顧客情報の取得は行わない。
当事者面談・有料試行は、別途実施を依頼された場合だけ進める。
```
